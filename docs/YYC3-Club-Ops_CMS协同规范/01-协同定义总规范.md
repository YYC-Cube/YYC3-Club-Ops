# 📐 协同定义总规范

> **一句话**：**App 是 B 端生产经营管理运维端**，门店级数据由 App 创建/编辑/变更并同步 CMS PC；**CMS 管中央配置、汇总、报表与纠正命令**；两者只通过**版本化 API + 事件**协作，**不共库、不双写、不直连**。

---

## 1. 目的与范围

### 1.1 目的

1. 为 B 端 App（Club-Ops）与 CMS（Clube-Management-System）建立**唯一、可执行、可验收**的协作边界。
2. 消除“商品/房型/价格/会员/艺人”等主数据在两侧重复维护的风险。
3. 确保房态、订单、账单、支付、交接、寄存、审批、任务等**交易事实只有一个写入源**。
4. 让报表、对账、审计有稳定的数据来源与时间口径。

### 1.2 范围

| 在范围 | 不在范围 |
|---|---|
| 中央配置同步（CMS→App） | 两个仓库的 UI 合并 |
| 门店运营数据同步（App→CMS） | 两套数据库的直接 SQL 访问 |
| 交易事件回传（App→CMS） | CMS 的现场收银功能 |
| 纠正命令（CMS→App） | 第三方支付网关内部实现 |
| 身份与权限边界 | 外部产品（智慧商家/巨嗨）的接口复刻 |
| 金额/时间/营业日口径 | 历史 Mock 数据的生产使用 |
| 对账、异常、审计、SLO | — |
| 环境、发布、变更治理 | — |

### 1.3 术语

| 术语 | 定义 |
|---|---|
| **中央配置（Central Config）** | 由 CMS 维护、App 只读的租户/集团级规则与模板：tenant/store 开通、全局模板、权限模板、报表定义 |
| **门店运营数据（Store Operational Data）** | 由 App 创建/编辑/变更的门店级数据：商品、价格、库存、房型、会员、员工档案、艺人、设置、仓库 |
| **交易事实（Transaction）** | 由 App 产生、CMS 只读的事实：房态会话、订单/账单、支付、交接、寄存、审批、任务 |
| **纠正命令（Correction Command）** | CMS PC 对门店级数据的受控修改请求；由 App 应用后回传结果，CMS 不直接改 App 事实 |
| **Outbox** | App 侧与业务事务同库写入的事件表，保证“业务成功 = 事件必达” |
| **投影（Projection）** | CMS 根据 App 事件构建的只读查询/报表模型，不反向写 App |
| **墓碑（Tombstone）** | 删除标记，防止两侧残留 |
| **营业日** | `Asia/Shanghai` 时区下，以 08:00 为日切点的业务日期 |

```text
│             │                         ┌──────────────────────┐     │

└─────────────┬────────────────────────────────────┬─────────────────┘
              │ ③ 中央配置发布                      │ ④ 事件入库/投影
              ▼                                    ▼
┌────────────────────────────────────────────────────────────────────┐
│               CMS PC（中央数据管理、汇总、报表、审计）                │
│  中央配置表 · 运营投影 operational_* · 交易投影 · 命令中心 · 报表    │
│  PostgreSQL: yyc3_yy（5432）                                        │
└─────────────▲──────────────────────────────────────────────────────┘
              │ ⑤ 纠正命令（CMS→App，App 应用后回传）
              │
        （命令由 App 轮询/拉取，不在 CMS 直接改 App 事实）
```

Club-Ops DB: `yyc3_club_ops`（5433）—— 只被 App/同步层访问

**硬边界**：

- Club-Ops 不读取 CMS 数据库；CMS 不读取 Club-Ops 数据库。
- 门店级数据第一写入方是 App；CMS PC 只做投影/汇总，修改门店字段走纠正命令。
- 中央配置第一写入方是 CMS；App 只读缓存。
- 报表由 CMS 投影，App 只查询 CMS 报表 API；App 不维护 98 张报表的生产库。
- 同步层只做搬运/转换/去重/命令下发，不做业务计算。

### 3.2 归属判定规则

1. **中央配置**（租户/集团级、一次配置全店生效）→ **CMS**。
2. **门店运营数据**（现场创建/编辑/变更）→ **App**，同步 CMS PC。
3. **交易事实**（资金/库存/房态）→ **App**，同步 CMS PC。
4. 同一实体若两侧都需要编辑 → **字段级拆分**（见 `04`），不得两端同时写同一字段。
5. CMS PC 对门店级字段的修改 → **纠正命令**，由 App 应用后回传；CMS 不直接改 App 事实。
6. 报表/指标永远由**事实源投影**，不允许手工在另一侧改数。
7. 任何新增实体/字段必须先登记级别、owner、同步方向，才能开发。

### 3.3 冲突裁决

| 场景 | 裁决 |
|---|---|
| App 改门店字段 vs CMS 中央模板 | 门店字段 App 胜；模板字段 CMS 胜 |
| CMS 纠正命令 vs App 并发编辑 | 版本冲突返回 `version_conflict`，重新下发 |
| 同一事件重复 | CMS 以 `eventId` 去重 |
| 旧 `recordVersion` | CMS 拒绝/忽略 |
| App 尝试写中央配置 | 403 `forbidden_central_write` |
| CMS 尝试直接写门店字段 | 必须走命令；直接写投影视为违规 |

## 4. 身份、权限与门店作用域

### 4.1 两类身份

| 身份 | 用途 | 认证方式 | 存储 |
|---|---|---|---|
| **用户身份** | 员工登录 App / CMS | App：HttpOnly Cookie + CSRF；CMS：JWT（后续可统一 SSO） | 各自会话体系 |
| **服务身份** | 同步层调用 CMS / App | HMAC-SHA256 签名 + 时间戳 + nonce；生产建议 mTLS | 密钥管理系统 |

**禁止**：用员工 JWT 做服务同步；把服务密钥写进前端/仓库；跨系统共享用户密码。

### 4.2 门店作用域

- 所有主数据与交易数据必须带 `tenantId + storeId`。
- CMS 侧新增 `tenant_id` 字段；过渡期用 `store_map` 映射（见 `04`）。
- App 所有请求使用 `/stores/{storeId}/...`；服务端二次校验会话授权。
- 同步事件必须携带 `tenantId/storeId`；缺失即拒绝。

### 4.3 角色映射（建议）

| CMS 角色 | App 角色 | 差异 |
|---|---|---|
| `ADMIN` | `admin` | CMS 管配置；App 管全店 |
| `MANAGER` | `manager` | 门店级管理 |
| `CASHIER` | `cashier` | 收银/交接 |
| `WAITER` | `waiter` | 点单/服务 |
| 新增：`WAREHOUSE`、`MARKETING`、`ARTIST_SUPERVISOR`、`SYSTEM` | 同名 | App 按职务可见模块 |

## 5. ID、编码与引用规范

| 对象 | 规则 | 示例 |
|---|---|---|
| `tenantId` | CMS 生成，全局唯一，不可变 | `tnt_01H...` |
| `storeId` | CMS 生成，全局唯一；App 侧保存映射 | `str_01H...` |
| 主数据实体 ID | CMS 生成，API 返回；App 不生成 | `prd_01H...` |
| 交易实体 ID | App 生成，UUIDv7/ULID，时间有序 | `ord_01H...` |
| 事件 ID | App 生成，UUIDv7；全局唯一 | `evt_01H...` |
| 订单号 `orderNo` | `{storeCode}-RO-{YYYYMMDD}-{6位序号}`；存量 `RO*` 保留 | `FLAGSHIP-RO-20261101-000123` |
| 账单号 `billNo` | `{storeCode}-ZD-{YYYYMMDD}-{6位序号}` | `FLAGSHIP-ZD-20261101-000045` |
| 幂等键 | 客户端生成；同一业务动作重试必须复用 | `checkout:{orderId}:{attemptGroup}` |
| 外部 ID 映射 | `source_system + source_id ↔ canonical_id` | `cms:store_1 ↔ str_01H...` |

**禁止**：用数据库自增 ID 跨系统传输；用名称作主键；同一业务动作每次重试生成新幂等键。

## 6. 金额、时间、营业日

| 维度 | 规范 |
|---|---|
| 金额 | 一律**整数分**（`*_cents`）；JSON 字段名带 `Cents`；禁止浮点/字符串元 |
| 币种 | `CNY`（当前唯一） |
| 时间 | ISO 8601 带时区，如 `2026-11-01T12:30:00+08:00`；数据库 `timestamptz` |
| 营业日 | `Asia/Shanghai`，08:00 日切；跨日订单归属开始营业日 |
| 计费 | 15 分钟进位 + 最低 1 小时（沿用 `lib/pricing.ts`）；变更需版本化 |
| 时间源 | 服务端唯一；客户端时间只用于展示 |
| 时区 | 门店级 `timezone`，默认 `Asia/Shanghai` |

## 7. API 通用规范

### 7.1 统一响应

```json
{
  "success": true,
  "data": {},
  "code": "ok",
  "message": "",
  "requestId": "req_01H...",
  "serverTime": "2026-11-01T12:30:00+08:00"
}
```

失败：

```json
{
  "success": false,
  "code": "validation_error",
  "message": "客户可读的错误说明",
  "details": [{ "field": "paymentMethod", "reason": "unsupported" }],
  "requestId": "req_01H...",
  "serverTime": "2026-11-01T12:30:00+08:00"
}
```

### 7.2 错误码（跨系统统一）

| 错误码 | HTTP | 含义 |
|---|---|---|
| `validation_error` | 400 | 参数/枚举/金额不合法 |
| `unauthorized` | 401 | 未登录/会话失效 |
| `forbidden_store` | 403 | 无门店权限 |
| `csrf_invalid` | 403 | CSRF 缺失/伪造 |
| `not_found` | 404 | 资源不存在 |
| `state_conflict` | 409 | 房态/订单状态不允许 |
| `idempotency_conflict` | 409 | 幂等键复用但载荷不同 |
| `version_conflict` | 409 | 数据版本过期/事件乱序/命令版本冲突 |
| `forbidden_central_write` | 403 | App 试图写中央配置 |
| `forbidden_field` | 403 | 写入不属于自己的字段 |
| `rate_limited` | 429 | 限流 |
| `sync_unavailable` | 503 | 同步层/依赖不可用 |
| `internal_error` | 500 | 未预期错误（不泄露内部细节） |

### 7.3 分页/筛选/排序

- `page` 从 1 开始；`pageSize` 默认 20，最大 200。
- 时间筛选统一 `from`/`to`（ISO8601 或营业日 `YYYY-MM-DD`）。
- 排序 `sort=field:asc|desc`；字段白名单。
- 导出单独端点，设置行数上限与审计。

### 7.4 写操作

- 用户写：`X-CSRF-Token` + 会话 Cookie（App）；CMS 按自身会话。
- 服务写：`X-YYC3-Signature` + `X-YYC3-Timestamp` + `X-YYC3-Nonce` + `X-YYC3-Key-Id`。
- 幂等：`Idempotency-Key`；服务端保存 24h~7 天。
- 审计：`actorId`、`storeId`、`action`、`before/after`（脱敏）、`requestId`。

### 7.5 版本

- URL 前缀 `/api/v1`；破坏性变更升 `/api/v2`。
- 事件类型带 `eventVersion`；字段只增不删，弃用先标记。
- OpenAPI 为唯一契约源；禁止“代码先改、文档后补”。

## 8. 同步总则

### 8.1 中央配置（CMS→App）

- **版本化**：每个 `tenant + domain` 有单调递增 `centralVersion`。
- **快照 + 增量**：首次/落后太多取快照；日常用 `since=centralVersion` 取增量。
- **墓碑**：删除以 `deleted=true` + `deletedAt` 表示，App 软删除。
- **应用原子性**：一批增量在一个事务内应用；`central_sync_version` 与数据同事务更新。
- **只读约束**：App 不得修改中央配置；写请求返回 `403 forbidden_central_write`。
- **历史快照**：订单/账单保存下单时的名称、单价、套餐快照，不随配置改价回写。

### 8.2 门店运营数据（App→CMS）

- **App 第一写入**：商品、价格、库存、房型、会员、员工门店档案、艺人、设置、仓库等由 App 创建/编辑/变更。
- **Outbox 同事务**：运营写表与 `sync_outbox` 同事务提交，事件类型 `master.*`。
- **字段 owner**：App 事件只允许改 `owner=app` 字段；CMS 拒绝 `forbidden_field`。
- **版本**：每条记录 `recordVersion` 单调递增；CMS 以 `aggregateId + recordVersion` 做顺序与幂等。
- **投影**：CMS 写 `sync_event_log` 后更新 `operational_*` 投影；可重放重建。
- **CMS PC 修改**：只能改中央配置字段；门店级字段必须走纠正命令。

### 8.3 交易事实（App→CMS）

- **Outbox 同事务**：业务表与 `sync_outbox` 在同一数据库事务提交。
- **至少一次**：失败重试；CMS 以 `eventId` 去重；重复返回 `duplicate`。
- **顺序**：同一聚合根按 `sequence` 递增；CMS 拒绝乱序（`version_conflict`）。
- **批量**：≤100 事件/批；单事件 ≤256KB；超限拆批。
- **死信**：超过重试上限进 DLQ，人工/脚本重放；重放不改变 `eventId`。
- **投影**：CMS 先写事件日志，再更新报表读模型；两者可重放重建。

### 8.4 纠正命令（CMS→App）

- CMS 生成命令 → App 拉取 → 校验权限/字段 → 应用 → 回传 `master.*` 事件 + ACK。
- CMS 在收到 ACK/事件前**不得**直接更新门店投影。
- 命令失败返回 `rejected` + 错误码；超过阈值告警。

### 8.5 冲突裁决

| 场景 | 裁决 |
|---|---|
| 中央配置 CMS/App 不一致 | CMS 胜；App 覆盖缓存 |
| App 尝试写中央配置 | 拒绝 403；不产生事件 |
| App 改门店字段 vs CMS 中央模板 | 门店字段 App 胜；模板字段 CMS 胜 |
| CMS 纠正命令 vs App 并发编辑 | 版本冲突 `version_conflict`，重新下发 |
| 事件重复 | CMS 去重，返回 duplicate |
| 事件乱序 | CMS 暂存/拒绝，App 重试 |
| 同一订单重复结账 | App 幂等键拦截；事件只发一次 |
| CMS 报表与 App 实时不一致 | 以对账结果为准；T+1 修正投影 |

## 9. 安全与合规

| 项 | 要求 |
|---|---|
| 传输 | 全站 HTTPS；生产禁用明文 HTTP（外部业务域例外需单独评估） |
| 服务认证 | HMAC-SHA256，时间戳 ±5 分钟，nonce 防重放；密钥 90 天轮换 |
| 用户认证 | App：HttpOnly + SameSite + CSRF；CMS：JWT 短时 + 刷新；不共享密码 |
| 授权 | 角色 × 门店 × 模块 × 动作；越权 403；审批人 ≠ 申请人 |
| PII | 手机号/身份证/照片/微信 openid 加密存储；日志与报表脱敏 |
| 审计 | 中央配置变更、门店运营数据变更、纠正命令、审批、退款、改价、交接、清空数据、同步重放全留痕 |
| 密钥 | 只进密钥管理系统；仓库/文档/前端 0 明文 |
| 依赖 | `pnpm audit` 高危为 0；新增依赖需评审 |
| 第三方 | 不复刻外部产品接口/品牌/素材；操作手册仅作功能参考 |

## 12. 治理与 RACI

| 事项 | R | A | C | I |
|---|---|---|---|---|
| 数据归属变更 | 架构组 | 项目负责人 | 两侧负责人 | 开发/运维 |
| 双向数据契约 | App 负责人 + CMS 负责人 | 架构组 | QA | 开发/运维 |
| 中央配置契约 | CMS 负责人 | 架构组 | App 负责人 | QA |
| 运营事件/交易事件契约 | App 负责人 | 架构组 | CMS 负责人 | QA |
| 纠正命令契约 | CMS 负责人 | 架构组 | App 负责人 | QA |
| 同步故障 | 运维 | 架构组 | 两侧开发 | 负责人 |
| 对账差异 | 财务/数据 | 项目负责人 | 两侧开发 | 运维 |
| 生产发布 | 运维 | 项目负责人 | QA/安全 | 全员 |

**变更原则**：先改契约 → 评审 → 双端实现 → 契约测试 → 灰度 → 全量；禁止“先上线再补契约”。

## 13. 验收总则

1. 两侧均通过 `05` 的联调用例与契约测试。
2. 中央配置在 App 侧只读；门店运营数据在 CMS 侧只读投影；交易在 CMS 侧只读投影。
3. 门店数据修改只由 App 写入并同步 CMS；CMS 对门店字段的修改必须通过纠正命令。
4. 任意一侧宕机 30 分钟，另一侧可继续本地交易/编辑/查询缓存，恢复后自动补偿。
5. 重复/乱序/超时/断网/命令冲突注入测试全部通过。
6. T+1 对账 0 差异；审计可追溯到人/门店/请求。
7. 文档、OpenAPI、字段映射、版本记录同步更新。
