# 🧮 对账、异常与联调验收

> **目标**：任何一笔交易都能在 App 与 CMS 找到同一事实；任何差异都能定位、解释、修复、留痕。
> **口径**：金额“分”、营业日 `Asia/Shanghai` 08:00 日切、时间 ISO8601。

---

## 1. 对账总览

### 1.1 对账时点

| 任务 | 时间 | 范围 |
|---|---|---|
| 实时监控 | 持续 | Outbox 延迟/DLQ/失败率 |
| 班次对账 | 每次交接班 | 当班订单/支付/交接单 |

| 月对账 | 每月 1 日 10:00 | 上月全量 + 会员/艺人/库存 |
| 主数据/中央配置对账 | 每小时 | 各域版本/条数/墓碑 |
| 门店运营数据对账 | 每小时/日 | 商品/价格/会员/员工/艺人/设置/仓库 条数与版本 |
| 纠正命令对账 | 每小时 | 下发/应用/拒绝/超时 |

## 2. 对账实现

### 2.1 App 侧汇总

> 以下 `business_date`、`paid_cents`、`refund_cents` 为对账所需的**新增字段/新表**（当前 `app.room_order` 只有 `total_cents` 与 `payment_method`），需在 App 迁移中补齐；不是现状。

```sql
-- 示例：按营业日汇总订单（目标结构）
SELECT
  store_id,
  business_date,
  count(*)                         AS order_count,
  sum(total_cents)                 AS total_cents,
  sum(paid_cents)                  AS paid_cents,
  sum(refund_cents)                AS refund_cents
FROM app.room_order
WHERE business_date = $1
GROUP BY store_id, business_date;
```

- App 生成 `reconciliation_daily` 表：`tenant_id, store_id, business_date, dimension, count, amount_cents, generated_at`。
- 对账数据本身也是**只读事实**，不手工修改。

### 2.2 CMS 侧汇总

- 从 `sync_event_log` + 投影表汇总，口径与 App 完全一致。
- CMS 生成 `reconciliation_result`：`store_id, business_date, dimension, app_count, cms_count, app_amount_cents, cms_amount_cents, diff_count, diff_amount_cents, status`。

### 2.3 差异判定

| 状态 | 条件 | 处理 |
|---|---|---|
| `matched` | count/amount 均为 0 差异 | 通过 |
| `count_diff` | 笔数不同 | 查丢失/重复事件 |
| `amount_diff` | 笔数同、金额不同 | 查金额字段/退款/折扣 |
| `missing_in_cms` | App 有、CMS 无 | 查 Outbox/DLQ |
| `missing_in_app` | CMS 有、App 无 | 查重复投影/手工导入 |
| `status_diff` | 金额同、状态不同 | 查事件顺序/投影逻辑 |
| `master_lag` | 中央配置/门店运营数据版本落后 | 查同步任务 |

## 3. 差异处置手册

### 3.1 通用步骤

```text
1. 锁定：标记该营业日/门店为“对账中”，暂停自动修正
2. 定位：按订单号/eventId/aggregateId 查两侧日志
3. 判断：丢失 / 重复 / 金额 / 顺序 / 主数据
4. 修复：
   - 丢失 → 从 App Outbox 重放
   - 重复 → CMS 去重并回滚重复投影
   - 金额 → 以 App 事实为准，重建投影
   - 顺序 → 补缺口后按序重放
   - 主数据 → 触发全量同步
5. 复核：重新对账至 0 差异
6. 留痕：记录差异单（门店/营业日/维度/原因/修复人/时间）
7. 复盘：若同类差异 ≥3 次，升级为缺陷并改契约/代码
```

### 3.2 绝对禁止

- ❌ 直接在 CMS 报表库改数“抹平”差异。
- ❌ 删除 App Outbox 事件来“消除”告警。
- ❌ 用另一笔订单冲抵差异（必须走正式调整单/退款流程）。
- ❌ 关闭对账任务换取“绿色”。

### 3.3 差异单模板

| 字段 | 说明 |
|---|---|
| `diffId` | 唯一编号 |
| `businessDate` / `storeId` | 范围 |
| `dimension` | orders/payments/handover/... |
| `appValue` / `cmsValue` | 笔数/金额 |
| `category` | 见 2.3 |
| `rootCause` | 丢失/重复/金额/顺序/主数据/代码缺陷 |
| `evidence` | eventId/orderNo/截图/日志链接 |
| `action` | 重放/重建/调整单/修复 |
| `owner` / `resolvedAt` | 责任人/时间 |
| `prevention` | 防再发措施 |

## 4. 监控与告警

| 指标 | 阈值 | 动作 |
|---|---|---|
| 中央配置/运营数据同步延迟 | P95 >60s | 告警 |
| 事件送达延迟 | P95 >5s | 告警 |
| Outbox pending | >1000 或最老 >60s | 告警 |
| DLQ | >0 | 立即告警 |
| 对账差异 | >0 | 08:30 告警，09:00 未清零升级 |
| 签名失败 | 5 分钟内 >10 | 安全告警 |
| 同步 API 5xx | >1% | 告警 |
| 中央配置/运营数据版本落后 | >5 分钟 | 告警 |

**看板**：同步健康（每域）、事件吞吐、DLQ 列表、对账差异趋势、Top 差异门店。

## 5. 联调环境

| 环境 | App | CMS | 数据 |
|---|---|---|---|
| `dev` | 本地 3030 + API 3032 | 本地 CMS + `yyc3_yy_dev` | 合成数据（非真实 PII） |
| `staging` | 预发域名 | 预发 CMS + 独立库 | 脱敏样本 + 压测数据 |
| `prod` | 生产域名 | 生产 CMS + `yyc3_yy` | 真实数据，最小权限 |

**要求**：

- 三套环境使用**不同密钥**、不同数据库、不同 bucket。
- 禁止把生产数据导入 dev/staging；需要样本时脱敏。
- 联调前双方提供：API 地址、服务 KeyId（不含 secret）、测试账号、门店/租户 ID、回调白名单。
