# 🔁 变更管理与版本记录

> **原则**：先契约、后代码；先兼容、后切换；任何破坏性变更都有灰度与回滚。
> **目标**：两侧独立发布时，不因版本差导致数据错、交易停、报表乱。

---

## 1. 版本体系

| 对象 | 版本方式 | 示例 |
|---|---|---|
| 文档 | 语义化 `vMajor.Minor.Patch` | `v1.0.0` |
| API | URL `/api/v1` | 破坏性升 `/api/v2` |
| 主数据域 | `tenant + domain` 单调版本 | `20261101001` |
| 事件 | `eventType` + `eventVersion` | `order.checkout.completed@1` |
| 字段 | 只增不删；弃用先标记 | `deprecatedAt` |
| 数据库 | 迁移文件序号 | `006_sync_outbox.sql` |

---

## 2. 变更类型

| 类型 | 示例 | 兼容性 | 审批 |
|---|---|---|---|
| **新增字段（可选）** | 商品加 `displayOrder` | 向后兼容 | 双方负责人 |
| **新增枚举值** | 支付方式加 `custom1` | 需双方忽略未知值 | 双方负责人 |
| **新增事件** | `artist.ticket.txn.posted` | 兼容 | 架构组 |
| **新增域** | `device` | 兼容 | 架构组 + 负责人 |
| **修改字段语义/单位** | 元→分 | **破坏性** | 项目负责人 |
| **删除/重命名字段** | `price`→`priceCents` | **破坏性** | 项目负责人 |
| **修改字段 owner/同步方向** | 商品由 CMS 改为 App 写 | **破坏性** | 项目负责人 + 架构组 |
| **修改主键/ID 规则** | 自增→ULID | **破坏性** | 项目负责人 |
| **修改同步方向/归属** | 会员改由 App 写 | **破坏性** | 项目负责人 + ADR |
| **修改认证/签名** | HMAC→mTLS | **破坏性** | 安全 + 负责人 |

## 3. 变更流程

```text
1. 提变更单（模板见第 4 节）
2. 影响分析：字段/事件/报表/历史数据/客户端版本
3. 契约评审：两侧负责人 + 架构 + QA + 安全
4. 更新文档：01~05 + OpenAPI + 字段映射
5. 双端实现：先兼容读，再兼容写，最后切换
6. 契约测试 + 沙箱联调
7. 灰度：1 门店 → 10% → 全量
8. 观察：对账/告警/错误率 ≥3 天
9. 全量 + 旧版本弃用公告
10. 归档：版本记录、回滚方案、证据
```

**禁止**：

- 先上线再补契约。
- 无灰度直接全量。
- 删除字段不留弃用期。
- 同一版本内改变字段含义。

## 4. 变更单模板

| 字段 | 内容 |
|---|---|
| `changeId` | `CHG-YYYYMMDD-序号` |
| `title` | 一句话 |
| `type` | additive / breaking / fix |
| `domains` | product/room/pricing/... |
| `events` | 新增/修改的事件 |
| `fields` | 新增/修改/删除字段 |
| `reason` | 业务/合规/性能原因 |
| `impact` | 影响 App 版本/CMS 版本/报表/历史数据 |
| `compatibility` | 兼容策略（双读/双写/开关） |
| `migration` | 数据迁移/回填脚本 |
| `rollback` | 回滚步骤与数据恢复 |
| `testPlan` | 契约/联调/对账用例 |
| `owners` | R/A/C/I |
| `schedule` | 灰度/全量时间 |
| `approval` | 签字记录 |

## 5. 兼容策略

| 场景 | 策略 |
|---|---|
| 新增字段 | 旧客户端忽略；新客户端可选读 |
| 新增枚举 | 双方必须有 `unknown` 兜底 |
| 字段单位变更 | 新旧字段并存（`price` + `priceCents`），双读一段时间后删除旧字段 |
| 事件结构变更 | 升 `eventVersion`；CMS 同时支持 v1/v2 解析 |
| 同步 API 变更 | `/v1` 与 `/v2` 并行；旧版只修安全，不加功能 |
| 数据库变更 | 先加列/回填/双写/切换/删列，分多迁移 |
| 认证变更 | 新旧 KeyId 双活 ≥30 天 |

## 6. 灰度与回滚

### 6.1 灰度

| 阶段 | 范围 | 观察 |
|---|---|---|
| S0 | 沙箱/合成数据 | 契约测试、对账 0 |
| S1 | 1 家门店（非高峰） | 错误率、延迟、对账 |
| S2 | 10% 门店 | 同上 + 财务抽查 |
| S3 | 全量 | 持续 3 天 |

**回滚触发**：交易失败率 >1%、对账差异 >0、DLQ >0、P0 缺陷、资金/库存不一致。

### 6.2 回滚步骤

```text
1. 关闭新版本入口（feature flag）
2. 停止新事件类型发送/接收
3. 回退 API 版本/客户端
4. 重建投影（按事件日志）
5. 对账确认 0 差异
6. 记录事故与根因
```

**数据不回滚原则**：交易事实不删除；通过反向事件/调整单修正；主数据回滚发布更高版本。

## 7. 弃用策略

| 项 | 规则 |
|---|---|
| 字段 | 标记 `deprecatedAt` + 替代字段；至少保留 2 个发布周期 |
| 事件 | 旧版本至少支持 90 天；公告 + 监控调用量 |
| API | `/v1` 弃用前 6 个月通知；提供迁移指南 |
| 客户端 | 最低支持版本公告；强制升级需灰度 |
