## 二、十条铁律（先读这一页）

1. **App = B 端生产经营管理运维端**：门店商品、价格、库存、房型、会员、员工档案、艺人、设置、仓库等由 App 创建/编辑/变更。
2. **CMS PC = 中央数据管理与汇总端**：接收 App 运营数据，提供跨店汇总、报表、审计、中央配置与必要纠正。
3. **中央配置方向**：CMS → App；App 只读缓存，不允许本地改中央配置。
4. **门店运营数据方向**：App → CMS；通过 Outbox/事件，CMS PC 不直接读 App 库。
5. **交易事实方向**：App → CMS；房态/订单/账单/支付/交接/寄存/审批/任务同样走事件。
6. **禁止双写**：同一字段只有一个写入方；CMS 对门店字段只能发纠正命令。
7. **禁止跨库 SQL**：`yyc3_club_ops`（5433）与 `yyc3_yy`（5432）不互连。
8. **金额只用“分”**：跨系统传输一律整数分；CMS 展示层再做元换算。
9. **时间只用 ISO8601 + 时区**：业务日 `Asia/Shanghai`，日切 08:00。
10. **幂等是默认**：所有写操作带 `Idempotency-Key`；所有事件带 `eventId` / `recordVersion`。

## 三、系统角色

| 系统 | 角色 | 不做什么 |
|---|---|---|
| **Club-Ops B 端 App** | 门店生产经营 + 交易 + 房态 + 商品/价格/会员/员工/艺人/设置编辑 + 任务/审批 | 不改中央配置；不做 98 张报表的生产库；不直连 CMS 库 |
| **CMS PC** | 中央配置 + 运营数据接收/汇总 + 报表 + 审计 + 纠正命令 | 不做现场收银；不直接写门店运营表；不直接改 App 库 |
| **同步层** | 中央配置下发、运营/交易事件回传、命令下发、重试、对账 | 不做业务判断；不合并两侧写入 |

## 四、当前状态与差距（必须如实说明）

| 能力 | CMS 现状 | 本规范要求 | 差距 |
|---|---|---|---|
| 多租户 | **无 tenant 模型**（Store 只有 `storeId`） | `tenantId + storeId` 全链路 | 需补 tenant 表/字段 |
| 中央配置 | 无系统化中央模板 | tenant/store 开通、全局模板、权限模板、报表定义 | 需新建 |
| 同步 API | 不存在 `/api/v1/sync/*` | 中央配置快照/增量 + 事件接收 + 命令 | 需新建 |
| 服务认证 | 用户 JWT（localStorage） | 服务间 HMAC/mTLS + 重放防护 | 需新建 |
| 运营数据投影 | 无 | `operational_*`（商品/房型/价格/会员/员工/艺人/设置/仓库/库存） | 需新建 |
| 事件入库 | 无 | 事件日志 + 去重 + 分支处理 + 投影 | 需新建 |
| 纠正命令 | 无 | 生成/下发/ACK/审计 | 需新建 |
| 对账 | 无 | 双向对账 + 差异报表 | 需新建 |
| API 真实性 | 大量 `mockService` | 真实仓储 + 契约测试 | 需替换 |

> **结论**：本规范是**目标契约**，不是 CMS 现状描述。CMS 未通过 `01` 第 10 章门禁前，不得作为生产同步后端。
