## 0. 评审结论

**方向正确，可以按此推进；但有 6 个 P0 必须在 W2/W6 前补齐，否则命令通道会在联调阶段返工。**

| 结论 | 说明 |
| --- | --- |
| ✅ 映射方向 | PC 不直接写门店事实；门店级数据走命令，App 应用后回传 `master.*` / `command.applied`；报表只读投影。方向与 `02/03` 一致 |
| ✅ 三个重点命令 | `catalog.import`、`stock.document`、`bill.correct` 的**用途判断正确**：分别覆盖批量商品导入、仓库六类单据、账单更正 |
| ❌ P0 缺口 | 三个命令均**缺少 payload/枚举/审批/幂等/部分成功**定义；W2 表清单**未按手册 9/12/10 子模块拆细**；存在“两个 08”命名冲突；artist_setting 写入方向已在 10 v1.3.0 统一（App 写、CMS 投影；PC 可写走命令） |
| 🟧 范围建议 | MVP 采用手册 **4 组报表/8 张核心**；98 张作为 Wave 2/3 扩展，不压进 Phase 1 |
| 🟥 不建议 | 直接按 `command.record.correct` 一个命令包打所有门店字段；`settings.update` / `device.update` 继续做“大杂烩” |

## 2. 三个重点命令逐项评审

### 2.1 `command.catalog.import`（商品批量导入）

| 项 | 现状（08） | 评审意见 |
| --- | --- | --- |
| 用途 | 批量导入商品/分类/口味/套餐 | ✅ 正确；但**单条新增/修改不应走 import**，应走 `record.upsert` |
| 触发 | PC 导入模板 → 下发 App → 回传 `master.product.*` | ✅ 方向正确；缺少“PC 先校验模板”的前置步骤 |
| 缺失字段 | — | 🟥 `importJobId`、`fileChecksum`、`fileName`、`rowCount`、`mode(validate/apply)`、`conflictPolicy(skip/update/abort)`、`dryRun`、`maxRows`、`errors[]` |
| 结果 | `command.applied/rejected` | 🟧 需要**逐行结果**（成功/跳过/失败）与汇总；部分成功必须明确 |
| 幂等 | 未定义 | 🟥 以 `importJobId + rowNo + checksum` 做幂等键；同一文件重复导入不得重复建品 |
| 事件 | `master.product.*` | ✅ 正确；需补 `sourceCommandId`、`importJobId` |
| 验收 | 未定义 | 100 行模板：成功/跳过/错误行可下载；重复导入 0 重复；失败可回滚/重试 |

**建议命令结构（示意）**

```json
{
  "commandType": "catalog.import",
  "commandId": "cmd_...",
  "idempotencyKey": "importJobId+fileChecksum",
  "storeId": "store_...",
  "payload": {
    "importJobId": "imp_...",
    "mode": "apply",
    "conflictPolicy": "update",
    "fileChecksum": "sha256:...",
    "rows": [
      { "rowNo": 1, "entity": "product", "operation": "create", "data": { "...": "..." } }
    ]
  },
  "expectedVersion": 1,
  "issuedBy": "user_...",
  "issuedAt": "2026-11-01T..."
}
```

### 2.2 `command.stock.document`（仓库单据）

| 项 | 现状（08） | 评审意见 |
| --- | --- | --- |
| 用途 | 采购/退货/调拨/报损/领用/盘点 | ✅ 正确；覆盖手册 6 类单据 |
| 缺失枚举 | — | 🟥 必须定义 `documentType`：`purchase`、`purchase_return`、`transfer`、`damage`、`requisition`、`count` |
| 缺失字段 | — | 🟥 `docNo`、`warehouseId`、`fromWarehouseId/toWarehouseId`（调拨）、`items[]{skuId,qty,unitCost,batchNo,expiry}`、`reason`、`attachments`、`expectedVersion`、`approvalId` |
| 主数据边界 | 08 §3.3 把仓库/供应商/出货仓/库存不足都列为 S | 🟥 这四项是**主数据**，应走 `command.record.upsert`；`stock.document` 只负责六类单据 |
| 审批 | 未定义 | 🟥 盘点/报损/调拨需审批或限额；盘盈盘亏需原因 |
| 幂等 | 未定义 | 🟥 `docNo` 唯一 + `idempotencyKey`；重复提交不得重复扣减库存 |
| 事件 | `inventory.*.posted` | ✅ 正确；需补 `sourceCommandId`、`documentType`、`docNo` |
| 验收 | 未定义 | 六类单据各 1 条：提交→App 应用→库存正确→事件回传→对账 0 差异 |

**建议 `documentType` 与事件映射**

| documentType | 事件 | 关键校验 |
| --- | --- | --- |
| `purchase` | `inventory.purchase.posted` | 供应商、单价、入库仓 |
| `purchase_return` | `inventory.purchase_return.posted` | 原采购单、退货数量 ≤ 入库数量 |
| `transfer` | `inventory.transfer.posted` | 出仓/入仓、同店跨仓/跨店策略 |
| `damage` | `inventory.damage.posted` | 报损原因、审批 |
| `requisition` | `inventory.requisition.posted` | 领用人、用途 |
| `count` | `inventory.count.posted` | 系统库存 vs 实盘、盘盈盘亏原因 |

### 2.3 `command.bill.correct`（账单制作/更正）

| 项 | 现状（08） | 评审意见 |
| --- | --- | --- |
| 用途 | 账单修改/删除/打印 → `bill.correct` | 🟥 **打印不属于账单更正**；打印走 `print_rule` / `command.device.print` |
| 操作枚举 | 未定义 | 🟥 必须定义 `operation`：`update`、`delete`、`batch_delete`、`keep_room_package_only` |
| 高危控制 | 只提“高危” | 🟥 需审批、金额阈值、双人复核、原因、修改前后快照 |
| 批量删除 | 08 未覆盖 | 🟥 在用系统“账单制作”有批量删除；必须限制条数/金额，并逐条审计 |
| 只保留开房套餐 | 08 未覆盖 | 🟥 需定义规则：删除哪些明细、是否保留房费/套餐、是否影响已支付/挂账 |
| 幂等/版本 | 未定义 | 🟥 `billId + expectedVersion + idempotencyKey`；并发修改返回 `version_conflict` |
| 事件 | `bill.adjusted` | ✅ 正确；需携带 `sourceCommandId`、修改前后摘要 |
| 验收 | 未定义 | 修改/删除/批量删除/只保留套餐 4 类用例；金额勾稽；审计可查 |

**建议命令结构（示意）**

```json
{
  "commandType": "bill.correct",
  "commandId": "cmd_...",
  "idempotencyKey": "billId+operation+expectedVersion",
  "payload": {
    "operation": "batch_delete",
    "billIds": ["bill_...", "bill_..."],
    "reason": "收银误操作",
    "approvalId": "appr_...",
    "beforeSnapshot": { "...": "..." },
    "limits": { "maxBills": 20, "maxAmount": 500000 }
  },
  "expectedVersion": 3,
  "issuedBy": "user_...",
  "issuedAt": "2026-11-01T..."
}
```

## 3. 命令体系缺口（08 未列或过粗）

| # | 缺口 | 影响 | 建议 |
| --- | --- | --- | --- |
| 1 | `command.record.correct` 命名与语义 | “correct”像纠错，但 08 用它做新增/修改/删除 | 改名/新增 `command.record.upsert`（operation=create/update/delete），保留 correct 仅纠正 |
| 2 | 缺少 `command.staff.import` | 08 §4 提到“员工批量导入”，命令表没有 | 新增；模板/校验/错误行同 catalog.import |
| 3 | 缺少 `command.movie.import` | 影片管理有导入，08 用 `device.update` 过粗 | 新增；影片文件/封面单独上传 |
| 4 | `command.settings.update` 过粗 | 门店设置/寄存/抹零/走马灯都塞一起 | 增加 `domain` 字段：`store_settings`、`deposit_rule`、`rounding_rule`、`marquee` |
| 5 | `command.device.update` 过粗 | 收银机/打印机/VOD/影片混在一起 | 拆 `command.device.update`、`command.vod.update`、`command.movie.import` |
| 6 | `command.artist_setting.update` 与 08 §3.6、10 §8 | 08 说 artist_setting 第一写入 App；10 v1.3.0 已统一 §2/§4/§8：App 写、CMS 投影 | 保持：App 写、CMS 投影；PC 页面若允许编辑走 `command.artist_setting.update`，App 应用后回传 `master.artist_setting.*` |
| 7 | 缺少 `command.booking.create` | 08 说在线预订“新增走命令或 App” | 明确 App 第一写入；PC 不新增，只查询/跟进 |
| 8 | 命令生命周期未定义 | 03 只有 `command.applied/rejected` | 补 `issued → delivered → applied/rejected → projected`；超时、重试、死信、人工介入 |
