# 🧭 ADR-001：多店 SaaS 定位与架构约束

## 状态

**已接受（Accepted）** —— 2026-10-31，由项目负责人确认。

## 背景

项目原名 F-KTV POS，现有实现以单店演示为目标：静态导出（`output: "export"`）、本地种子数据、无鉴权、无后端。首次审核确认其无法承载真实收银。负责人明确将产品定位调整为**多店 SaaS**，并要求按 Phase 1 直接修改源码。

## 决策

> **产品定位为多店 KTV 运营 SaaS：一个平台服务多个门店/商户，门店数据必须隔离，权限必须按角色与门店收敛，所有资金/库存/订单事实以服务端为准。**

Phase 1 只做工程止血与最小闭环，不引入半成品后端；Phase 2 起按本 ADR 落地多租户能力。

## 关键约束（不可协商）

| 维度 | 约束 |
| --- | --- |
| 租户模型 | 至少两级：`tenantId`（商户/品牌）+ `storeId`（门店）；所有业务实体必须携带 `storeId` |
| 数据隔离 | 服务端强制过滤；数据库启用行级安全（RLS）或等价的强制作用域；禁止仅靠前端过滤 |
| 身份认证 | 统一登录；会话使用 HttpOnly Cookie 或短时 JWT + 刷新；禁止长期 Token 存 localStorage |
| 权限 | 角色 × 门店 × 动作矩阵；越权返回 403；敏感操作（改价、退款、折扣、结账）单独审计 |
| 资金 | 金额以“分”或 decimal 字符串传输与存储；订单/支付/退款必须在事务内；支付回调幂等 |
| 时间 | 服务端为唯一时间源；门店时区可配置；报表口径明确（自然日/营业日） |
| 配置 | 门店级配置（打印、支付、房型、价格）与租户级配置分层 |
| 部署 | 静态导出仅限开发预览；生产必须使用支持服务端的运行环境 |

## 目标架构（Phase 2 建议）

```text
┌─────────────────────────────────────────────────────┐
│ Web (Next.js)                                       │
│  - 收银台 / 管理端                                   │
│  - 门店上下文（tenant/store 切换）                    │
│  - 仅做展示与校验，不承担最终一致性                   │
└──────────────────────┬──────────────────────────────┘
                       │ HTTPS / JSON
┌──────────────────────▼──────────────────────────────┐
│ API 服务（Node）                                     │
│  - 认证/会话、RBAC、门店作用域                        │
│  - 房间/订单/库存/会员/报表                            │
│  - 幂等键、审计日志、限流                             │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│ PostgreSQL（RLS） + Redis（会话/幂等/缓存）            │
│  - tenant_id / store_id 索引与复合唯一约束             │
│  - 订单/支付/库存事务                                  │
└─────────────────────────────────────────────────────┘
```

**建议选择**：

- Phase 2 先采用 **Next.js Node 运行时（移除 `output: "export"`）+ PostgreSQL + Prisma/Drizzle**，以最低迁移成本打通闭环；API 路由按领域拆分。
- 当门店数/并发上来后，再把 API 提取为独立服务；不要让前端直接连数据库。
- 数据库隔离优先 **共享库 + `store_id` + RLS**（成本低、易跨店报表）；出现强合规/大客户隔离诉求时再评估 schema-per-tenant。

## 对现有代码的影响

| 现状 | 处理 |
| --- | --- |
| `output: "export"` + GitHub Pages | Phase 2 迁移到支持服务端的托管；Pages 仅保留预览 |
| `lib/types.ts` 与 store 各有一套模型 | Phase 2 契约先行，收敛为单一事实源；`storeId` 必填 |
| `useRoomStore` 本地种子 | Phase 2 改为服务端查询 + 命令式接口；保留乐观更新但必须回滚 |
| `apiClient` 显式 Mock | Phase 1 已禁止静默降级；Phase 2 改为真实网关客户端 |
| 无认证/无 RBAC | Phase 4 落地登录、会话、角色矩阵、审计 |
| 报表/会员/库存/员工/设置占位 | Phase 3 按门店作用域实现 |

## Phase 1 已执行的支撑项

- 固化 `pnpm-lock.yaml` 与 `packageManager`，CI 使用 `--frozen-lockfile`。
- 升级 Next 15.5.28，清理 critical/high 依赖漏洞（审计结果 0）。
- 打开 TypeScript / ESLint / 单测 / E2E / 审计门禁。
- 房间模型增加 `storeId`，状态机显式化（开房→消费中→待清洁→空闲）。
- API 客户端改为显式 Mock，失败抛 `ApiError`。
- 金额工具统一“分”单位，新增测试。
- 线上/界面标注“开发预览 · 非生产”。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 多租户越权（IDOR） | 所有查询强制 `storeId` 作用域 + RLS + 契约测试 |
| 跨店数据泄露 | 禁止前端传任意 storeId；由会话中的门店上下文决定 |
| 支付回调重复/乱序 | 幂等键 + 状态机 + 对账任务 |
| 共享库热点门店 | 索引/分区/读写分离按数据验证，不提前过度设计 |
| 静态站误当生产 | 页面常驻“开发预览 · 非生产”标识 + README 声明 |
| 迁移期双写不一致 | 不做双写；按门店灰度切换，保留回滚开关 |

## 待确认（Phase 2 启动前）

1. 租户/门店层级命名与归属（品牌方是否可管多个门店）。
2. 后端实现归属：Next.js API 还是独立服务；由谁负责。
3. 数据库与部署环境（云厂商、区域、合规）。
4. 支付渠道与结算主体。
5. 门店时区与营业日口径。
6. 是否需要跨店/跨租户汇总报表及其权限。
