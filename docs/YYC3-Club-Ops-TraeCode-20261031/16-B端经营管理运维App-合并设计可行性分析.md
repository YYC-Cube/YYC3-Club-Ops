# 🧩 B 端「经营管理运维 App」合并设计可行性分析

> **输入**
> - 当前底座：`/Users/yanyu/YYC-Cube/personal/YYC3-Club-Ops`（Next 15 + React 19 + Tailwind 4 + Hono + PG RLS）
> - 面板参考：`/Users/yanyu/YYC-Cube/personal/YYC3-Futuristic-Dashboard`（收银房态面板 + 经营看板，Mock 驱动）
> - 功能基线：`docs/YYC3-智慧商家-双端功能体系与操作手册`（外部产品实抓：PC 运营中心 + App 5 Tab/20 模块）
> - 数据后台：`/Users/yanyu/YYC-Cube/personal/YYC3-Clube-Management-System`（已定位为「同步的后端数据管理」）
>
> **结论先行**：**可以合并“设计”，不能直接合并“代码”**。
> 正确路径是：**以操作手册为信息架构基线 + 以 Dashboard 为房态/收银面板视觉参考 + 以 Club-Ops 为技术底座 + 以 CMS 为后端数据管理与同步中心**，产出一个支持 **PC 桌面 + App/PWA 双形态**的 B 端「经营管理运维 App」。

## 0. 结论速览

| 问题 | 结论 | 依据 |
|---|---|---|
| 能否把 Club-Ops docs 与 Dashboard 合并为 B 端 App？ | **可以（设计层）** | 操作手册已给出完整 IA 与 20+ 现场模块；Dashboard 已有房态、POS、看板、多店面板；Club-Ops 已有真实房态/POS/会话/RLS |
| 能否把两个仓库直接合并成一套代码？ | **不可以（代码层）** | Dashboard 为 Next 16 + Tailwind 3 + 全 Mock + shadcn default；Club-Ops 为 Next 15 + Tailwind 4 + 真实 API + shadcn new-york；同路径源码仅 58/88 一致，业务组件已分叉 |
| Dashboard 还有没有价值？ | **有，作为“面板原型/视觉参考”；冻结决策已确认（2026-11-01，执行见 `17`）** | 房态面板 765/823/1043 行、POS 432 行、导航 1450 行、多店 715 行，交互密度高；但数据层不可复用 |
| CMS 是否应并入 App？ | **不应并入 UI，应作为后端数据管理/同步中心** | CMS 有 93 个 API 与后台页面，但大量 API 仍走 `mockService`；认证仍是模拟账号；与 App 的技术栈/版本/权限模型不同 |
| 最合理的产品形态 | **一个 B 端 App，两套布局（桌面运营中心 + 移动作业台）** | 符合手册「PC 建数据、App 做交易」的铁律，也符合“经营管理运维”三域划分 |
| MVP 范围 | **房态 + POS + 审批 + 交接 + 寄存 + 任务** 六个闭环 | 当前只有房态/POS 真实闭环；审批/交接/寄存/任务完全缺失，且是现场管理核心 |

## 1. 概念对齐：B 端、双端、经营管理运维

### 1.1 术语

| 术语 | 本文含义 |
|---|---|
| **B 端** | 商家/门店侧（老板、店长、收银、仓管、营销、艺人主管、系统管理员），对应 C 端顾客/会员 |
| **双端** | 同一套业务能力的两种形态：**桌面运营中心（配置+数据+报表）** 与 **移动作业台（现场交易+房态+任务）** |
| **经营** | 营收、报表、多店对比、会员资产、商品毛利、艺人产出 |
| **管理** | 人（员工/权限）、货（商品/库存/仓库）、场（包厢/房态/预订/排队）、钱（账单/支付/挂账/交接） |
| **运维** | 门店设置、打印/收银机、VOD/设备、报修、日志、审计、审批防线 |

### 1.2 与操作手册的对应

操作手册描述的外部产品是「PC 数据管理后台 + iOS 操作 App」：

- **PC 运营中心** = 配置中心 + 数据中心：建商品、定价格/套餐/计费、配权限/密码/审批、看 98 张报表。
- **App（智慧商家）** = 现场执行端：5 Tab（收银/AI客服/查看/AI工具/设置），收银首页 20 模块。
- **铁律**：**基础数据与规则只在 PC 建，现场交易只在 App 做**。

本方案保留这条铁律，但把两端收敛为**一个 B 端 App 的两套布局**，避免维护两套前端：

| 形态 | 主要用户 | 主要场景 | 布局 |
|---|---|---|---|
| **桌面运营中心** | 老板/店长/运营/财务/系统管理 | 建数据、定规则、看报表、审配置 | 左侧栏 + 多标签页 + 宽表格 |
| **移动作业台** | 收银/服务员/仓管/艺人主管 | 开房、点单、结账、审批、交接、巡场 | 底部 5 Tab + 宫格 + 大按钮 |

> 桌面与移动共享同一套路由、组件、权限与 API，只是 `layout` 与信息密度不同；不是两个独立工程。

## 2. 合并可行性判定

### 2.1 三个仓库的“可合并度”

| 对象 | 设计可合并 | 代码可合并 | 结论 |
|---|---|---|---|
| **Club-Ops** | — | — | **底座**：保留并演进，不替换 |
| **Futuristic-Dashboard** | ✅ 高 | ❌ 低 | **只取面板设计与交互模式**；数据层/状态层不迁移；**已冻结（2026-11-01，见 `17`）** |
| **Clube-Management-System** | ✅ 作为数据后台 | ❌ 低 | **不进 App 仓库**；通过 API/同步层对接 |
| **操作手册（外部实抓）** | ✅ 高 | — | **功能基线**；需转化为自有规格，不能直接当本项目 PRD |

### 2.2 为什么不能直接合并代码

| 阻塞项 | Dashboard | Club-Ops | 影响 |
|---|---|---|---|
| 框架 | Next 16.3.6 | Next 15.5.28 | App Router/API 约定、依赖版本不一致 |
| Tailwind | 3.4 + `tailwind.config.js` | 4.1 + CSS-first | shadcn 令牌/类名/主题不兼容 |
| 组件风格 | shadcn **default** | shadcn **new-york** | 同组件视觉与 API 有差异 |
| 数据层 | `lib/api/client.ts` 全 Mock | Hono + PG + 会话 + CSRF | Dashboard 的 store/service 无法直接接真实 API |
| 状态语义 | `useMultiStore` 前端门店列表 | `tenant + store + RLS` | 多租户语义不同，直接合并会破坏隔离 |
| 测试 | Vitest，24 用例自述 | Vitest，150 用例 | 可共用工具，但测试基线不可混 |
| 认证 | NextAuth beta 声明 | 自研 HMAC + HttpOnly + CSRF | 安全模型冲突 |

**结论**：只能做**“设计吸收 + 组件重写”**，不能做 `git merge` 或目录级复制。

### 2.3 可复用的 Dashboard 资产（按“设计价值”而非“代码价值”）

| Dashboard 资产 | 规模 | 可复用方式 | 处置 |
|---|---:|---|---|
| `room-status-dashboard.tsx` | 823 行 | 左侧状态统计、色块房卡、筛选/视图切换、一键清扫/开房 | **重写为 OPS `RoomBoard`**（接真实 API） |
| `enhanced-room-dashboard.tsx` | 765 行 | 分区/房型/状态筛选、房卡信息密度 | 同上，合并为一个可配置面板 |
| `seasonal-room-dashboard.tsx` | 1,043 行 | 节日皮肤/主题化思路 | 仅保留主题令牌思路，不迁移代码 |
| `pos-system.tsx` | 432 行 | 商品超市 + 购物车 + 支付方式 + 小票版式 | **以 OPS POS 逻辑为主，吸收其布局** |
| `navigation-system.tsx` | 1,450 行 | 分组导航/权限菜单雏形 | 仅参考 IA，不迁移（过重） |
| `multi-store/page.tsx` | 715 行 | 多店卡片/满包率/翻台率/门店切换 | 参考视觉，数据改接 OPS 多店 API |
| `analytics-dashboard.tsx` | — | KPI + 包厢利用率 + 商品销售 | 参考图表组合，数据改接报表 API |
| `member/product/inventory/employee` 组件 | — | 表单/表格/权限矩阵版式 | 参考字段分组，业务模型重写 |

> **不建议迁移**：Dashboard 的 Mock stores、`useMultiStore`、`useMembershipStore`、`useInventoryStore`、假登录 store、AI/5G/IoT 演示页。

### 2.4 四种合并路径对比

| 路径 | 做法 | 优点 | 致命问题 | 结论 |
|---|---|---|---|---|
| A | 以 Dashboard 为主，接 OPS 后端 | 面板现成 | Tailwind3/Next16/Mock 架构；无服务端；安全底座缺失 | ❌ |
| B | 把 Dashboard 目录合并进 OPS | 视觉直接复用 | 同路径 30 个文件已分叉；Mock 语义污染真实 API；两套主题冲突 | ❌ |
| C | 新建独立 B 端 App 仓库，调 CMS API | 边界清晰 | CMS 大量 Mock/认证未就绪；双端布局需从零；数据契约缺失 | ⚠️ 成本高 |
| **D（推荐）** | **OPS 演进双布局 + Dashboard 设计吸收 + CMS 数据后台** | 复用真实房态/POS/RLS；设计有参考；数据有归属 | 需重写面板、补 6 大闭环、建同步层 | ✅ |

> 推荐 D 的核心理由：**交易事实必须写在有 RLS/CSRF/幂等的一侧**（OPS），**主数据必须写在有后台管理能力的一侧**（CMS），**视觉密度从 Dashboard 借**。三者职责清晰，避免任何一方被“合并”成四不像。

**冲突规则**：
- 门店级字段以 **App 为准**；中央配置字段以 **CMS 为准**。

### 5.3 API 规划（MVP 新增）

| 域 | 建议端点 | 说明 |
|---|---|---|
| 工作台 | `GET /stores/{storeId}/workbench` | 汇总房态、今日营收、预警、待办、交接差异 |
| 任务 | `GET/POST /stores/{storeId}/tasks`、`PATCH /tasks/{id}` | 6 类任务（收钱/备货/送货/呼叫/清扫/存取酒） |
| 审批 | `GET/POST /stores/{storeId}/approvals`、`POST /approvals/{id}/approve` 或 `/reject` | 赠送/退款/报修/客遗四类 |
| 交接 | `POST /stores/{storeId}/handovers`、`GET /handovers` | 交接班/营业收入交接，生成交接单 |
| 寄存 | `GET/POST /stores/{storeId}/deposits`、`POST /deposits/{id}/withdraw` | 存酒/取酒/到期充公 |
| 挂账 | `GET/POST /stores/{storeId}/credits`、`POST /credits/{id}/repay` | 担保人/包厢/逐笔还款 |
| 预订/排队 | `/bookings`、`/queues` | 预订验证/新增/叫号 |
| 会员 | `/members`、`/members/{id}/recharge` | App 写入并同步 CMS |
| 库存 | `/inventory/counts`、`/inventory/stock` | 盘点/实时库存，App 写入并同步 CMS |
| 艺人 | `/artists`、`/artists/clock`、`/artists/fees` | 按 `05` 规格书，App 写入并同步 CMS |
| 报表 | `/reports/{code}` | 先做 8 张核心，查 CMS 投影 |
| 设置 | `/settings`、`/devices`、`/printers` | 门店设置 App 写；中央默认 CMS 只读 |
| 同步（对外） | `GET /sync/master/{domain}`、`POST /sync/events/batch`、`GET /sync/commands` | 中央配置、运营/交易事件、纠正命令 |

> 统一约定：分页 `page/pageSize ≤ 200`；错误码沿用 `lib/types.ts` 的 `code`；金额一律“分”；营业日 `Asia/Shanghai` + 08:00 日切；写操作必须 CSRF + 门店授权 + 幂等键；门店运营写操作必须同事务写 Outbox。

### 5.4 与 CMS 的对接方式

| 通道 | 适用 | 说明 |
|---|---|---|
| **中央配置（CMS→App）** | tenant/store 开通、全局模板、权限模板、报表定义 | CMS 发布版本化快照；App 只读缓存 |
| **门店运营数据（App→CMS）** | 商品/价格/库存/房型/会员/员工档案/艺人/设置/仓库 | App 写本地事务 + Outbox；`master.*` 事件同步 CMS |
| **交易回传（App→CMS）** | 订单/账单/支付/交接/寄存/审批/任务 | 同一 Outbox；CMS 只读投影 |
| **纠正命令（CMS→App）** | CMS 对门店错误数据的受控修正 | App 拉取/应用/ACK；不直接改 App 事实 |
| **报表查询** | 报表/指标 | App 经营页查 CMS 只读模型 |
| **禁止** | 双写同一张表、跨库直连 CMS 业务表 | 会破坏租户隔离与审计 |

**CMS 当前能力提醒**：虽然已有 93 个 `route.ts`，但大量接口仍调用 `lib/api/mock-service`（如 `/api/products`），登录仍是模拟账号；**在补齐真实仓储、认证、租户校验与契约前，不能把它当作可靠的生产同步后端**。

## 6. 权限与安全模型

### 6.1 权限模型（对齐手册“职务决定模块可见性”）

```
User → 员工档案 → 职务(role) → 组别(group) → 管辖门店(stores) → 模块可见性
                                                   ↓
                                       操作级权限（查看/创建/编辑/审批/导出）
                                                   ↓
```

|---|---|---|---|---|---|
| 老板/主账号 | 全 | 全 | 全 | 全 | 全 + 高危审批 |
| 店长 | 全 | 全 | 全 | 全 | 门店设置（受限） |

| 收银 | 房态 | POS/交接/寄存 | 会员/挂账 | 日报（只读） | — |
| 服务员 | 房态/任务 | 点单/呼叫 | 客遗 | — | — |
| 仓管 | — | — | 库存/盘点/调拨 | 库存报表 | — |
| 营销 | 房态 | 预订 | 会员/营销/客户 | 会员/营销报表 | — |
| 艺人主管 | — | — | 艺人域 | 艺人报表 | 艺人设置（只读） |
| 系统管理 | — | — | — | — | 全（配置/打印/设备/日志） |

### 6.2 安全底线（必须在 App 侧落实）

| 项 | 要求 |
|---|---|
| 会话 | 复用 Club-Ops：HttpOnly Cookie + HMAC + CSRF + 滑动续期 + 绝对上限 |
| 门店隔离 | 所有请求走 `/stores/{storeId}/...`；服务端再次校验；前端二次防御 |
| 高危操作 | 经理打折/赠送/挂账/退款/清空数据：密码 + 二次确认 + 审计 |
| 审批 | 四类审批默认开启；高额阈值可配置；审批人不能是申请人 |
| 金额 | 全链路“分”；服务端唯一计算；禁止前端传最终金额 |
| 审计 | 登录、审批、改价、退款、交接、设备重启全留痕 |
| 外部文档 | 手册 README 与 04 SOP 记录了外部系统的本地凭据库路径；**必须从仓库文档删除或脱敏**，真实凭证只进本地密钥库，不入库、不传播 |
| 第三方 | 操作手册为外部产品实抓；**不得复制其品牌名、Logo、文案、截图作为自有产品素材** |

## 7. 核心闭环设计（MVP 六条）

### 7.1 房态与开房

```text
工作台 → 房态看板（筛选区域/房型/状态）
→ 点房卡 → 空房: 计时/套餐/包断/预买开房（接房型+计费规则）
→ 消费中: 点单/结账/转房/续时/寄存/送花/远程点歌
→ 清洁: 一键完成 → 空闲
→ 维修: 原因必填 → 维修中 → 恢复营业
```

**复用**：Club-Ops `room-state.ts` 状态机 + API；Dashboard 色块卡片/左侧统计/四键快捷。

### 7.2 POS 点单结账

```text
包厢详情/交易 Tab → POS
→ 商品超市（分类/搜索/扫码）→ 购物车 → 挂单/挂单列表
→ 结账：房费 + 商品 + 服务费 + 低消补差 → 支付方式（现金/微信/支付宝/会员卡/挂账）
→ 幂等提交 → 小票 → 房态转“待清洁”
```

**复用**：Club-Ops 已有价目表、账单、退单、支付方式、幂等、小票（`14` 文档）；Dashboard POS 的布局与商品卡样式可参考。

### 7.3 审批中心

```text
申请人（App）提交赠送/退款/报修/客遗
→ 审批中心（按类型/门店/状态/等待时长）
→ 审批人核对金额/商品/包厢 → 通过/不通过（备注必填）
→ 通过后执行：扣库存/退款/赠送入账/报修工单/客遗入库
→ 全链路审计 + 报表
```

### 7.4 收银交接

```text
交易 Tab → 交接班 → 选择门店/班次 → 汇总当班现金流（现金/刷卡/微信/支付宝/挂账/会员）
→ 生成交接单 → 打印签字 → 营业收入交接（门店时段总额，非个人）
→ 与 CMS 交接汇总报表双向核对（差异 → 支付流水定位）
```

### 7.5 寄存/存酒

```text
管理/交易 → 寄存 → 新增存酒单（商品/数量/手机号/包厢/服务员/到期）
→ 生成存酒码/二维码 → 取酒验证 → 到期自动充公
→ 寄存/取酒/充公三套报表
```

### 7.6 任务与预警

```text
工作台 → 我的任务（收钱/备货/送货/呼叫/清扫/存取酒）
→ 任务来源：订单/呼叫/补货/清扫/寄存
→ 接收/完成/超时 → 消息中心 + 首页横幅 + 交接班检查
```

### Phase 1：现场闭环（第 2~4 周）

- App 壳：`(workbench)`/`(trade)`/`(manage)`/`(insight)`/`(settings)` 路由组 + 双布局。
- 房态看板：合并 Dashboard 视觉 + OPS 真实数据；支持区域/房型/状态筛选、四键快捷、房卡详情。
- POS：扫码/分类/购物车/挂单/结账/支付方式/小票；复用 `14` 的幂等与库存扣减。
- 审批中心：四类审批 + 待办角标 + 审计。
- 交接班/营业收入交接：生成交接单 + 打印占位 + 差异提示。
- 寄存/存酒：新增/取酒/到期（先手动，后自动充公）。
- 任务中心：6 类任务 + 首页预警。

### Phase 2：管理扩展（第 5~8 周）

- 会员：档案/等级/充值/权益/积分（与 CMS 主数据同步）。
- 库存：盘点/实时/调拨/报损/领用（移动建单 + 桌面审核）。
- 预订/排队/客户/客遗/挂账。
- 经营看板 + 运营日报 + 8 张核心报表。
- 员工/职务权限/管辖门店（读 CMS 主数据）。

### Phase 3：深度域（第 9~12 周）

- 艺人域：按 `05` 规格书 MVP（档案/等级/组别/台费规则/上下钟/报备/台费流水）。
- 仓库全量：供应商/采购/退货/调拨/盘点/寄存。
- 报表扩到 20 张；导出/打印。
- 打印/收银机/VOD/报修/设备状态。

### Phase 4：多店与生产（第 13~16 周）

- 多店房态总览（满包率/翻台率/收益对比）。
- CMS 双向同步 + 对账 + 死信告警。
- PWA/离线兜底；弱网重试。
- 生产加固：备份/监控/SLO/审计/压测。

## 11. 风险与对策

| ID | 风险 | 等级 | 说明 | 对策 |
|---|---|---|---|---|
| R1 | 把外部产品当自有 PRD | **高** | 手册是第三方产品实抓，含其品牌/流程/文案 | 只取功能结构；自有文案/组件/品牌；文档标注“外部对标” |
| R2 | 直接复制 Dashboard 代码 | **高** | Tailwind3/Next16/Mock 与底座不兼容 | 只参考视觉；组件重写并接真实 API |
| R3 | CMS 被误当可靠后端 | **高** | 93 API 中大量 Mock；登录模拟账号 | 先补真实仓储/认证/租户/契约；未达标前不接生产同步 |
| R4 | 范围爆炸（98 报表/100+ 开关/25 艺人） | **高** | 一次全做无法上线 | MVP 六闭环；报表 8 张；设置 20 开关；艺人独立分期 |
| R5 | 双写导致数据不一致 | **高** | CMS PC 直接改门店数据 / App 同时写 | 字段 owner + 纠正命令；Outbox/事件；禁止跨库直写 |
| R6 | 多租户与单店语义冲突 | 中 | 手册是单店（皇家国际），OPS 是 tenant+store | 所有新表强制 storeId；配置分租户/门店两级 |
| R7 | 移动端性能/弱网 | 中 | 房态/POS 需实时 | 路由级懒加载、虚拟列表、乐观更新 + 失败回滚、PWA 缓存 |
| R8 | 打印/设备集成不可控 | 中 | 打印机/VOD/门锁品牌差异 | 先做适配层接口 + 模拟设备；按门店实施 |
| R9 | 权限矩阵过细 | 中 | 9 角色 × 模块 × 门店 × 操作 | 先角色-模块，操作级后置；用配置表而非硬编码 |
| R10 | 文档凭据泄漏 | **高** | README/04 SOP 记录了外部系统的本地凭据库路径 | 立即脱敏；CI secret 扫描 |
| R11 | 品牌混淆 | 中 | “智慧商家/巨嗨/皇家国际”与自有品牌混用 | 自有产品命名（建议 `YYC³ Club Ops Workbench`） |

## 12. 验收标准（合并设计是否成立）

- [ ] 一个仓库、一套路由、两套布局（桌面/移动），无第二套前端工程。
- [ ] 工作台/交易/管理/经营/设置 五个一级域齐全，且与手册 20 模块有映射表。
- [ ] 房态看板接真实 API，支持筛选、统计、四键快捷、房卡详情、实时刷新。
- [ ] POS 完成“商品→购物车→挂单→结账→支付→小票→房态转清洁”闭环，幂等可重放。
- [ ] 审批中心支持四类审批，通过/驳回后产生对应业务副作用与审计。
- [ ] 交接班生成交接单，可与营业日报核对，差异可定位到支付流水。
- [ ] 寄存支持新增/取酒/到期；三张寄存报表可查。
- [ ] 任务中心覆盖 6 类任务，首页有预警与待办角标。
- [ ] 角色-模块可见性生效；高危操作有密码/二次确认/审计。
- [ ] 中央配置只从 CMS 同步；门店运营数据只从 App 回传；无跨库直写。
- [ ] 文档中无外部系统凭证路径/真实凭据；无第三方品牌素材。
- [ ] Dashboard 仓库标记为 ARCHIVED；其面板设计已吸收，不再单独维护。
- [ ] 关键页面在 375px/768px/1440px 三种宽度可用。
- [ ] 单元测试覆盖房态/POS/审批/交接关键状态机；E2E 覆盖六条主流程。

## 13. 待确认问题（决定 MVP 边界）

1. **B 端 App 的配置边界**：门店级配置（商品/价格/会员/员工档案/艺人/设置）由 App 编辑；中央模板（租户/全局/权限/报表）只在 CMS PC 维护——是否认可？
2. **MVP 六闭环**（房态/POS/审批/交接/寄存/任务）是否认可？是否要加入会员或库存？
3. **字段 owner**：商品/价格/套餐/员工档案/设置等门店字段由 App 写、CMS 只读投影；中央身份/模板由 CMS 写——字段边界是否认可？
4. **艺人域**：按本方案由 App 写、CMS 汇总报表；是否仍有 CMS PC 侧艺人维护需求？
5. **多租户**是否 MVP 必须支持，还是先单店、后续开多店？
6. **形态**：PWA 优先，还是必须原生 iOS/Android（打印/扫码/摄像头）？
7. **设备**：打印机/收银机/VOD/门锁/售货柜的首批对接清单与品牌？
8. **命名**：是否采用 `YYC³ Club Ops Workbench`（或你指定的品牌名）？
