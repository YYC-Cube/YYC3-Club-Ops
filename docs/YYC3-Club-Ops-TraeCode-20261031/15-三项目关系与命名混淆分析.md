# 🧭 三项目关系与命名混淆深度分析

> **分析对象**
> - 当前项目：`/Users/yanyu/YYC-Cube/personal/YYC3-Club-Ops`
> - 对比项目 A：`/Users/yanyu/YYC-Cube/personal/YYC3-Futuristic-Dashboard`
> - 对比项目 B：`/Users/yanyu/YYC-Cube/personal/YYC3-Clube-Management-System`
>
> **分析方式**：只读静态审计 + Git 历史/血缘 + 文件哈希比对 + 配置/部署/文档核查
> **分析原则**：以代码与仓库事实为准；推断显式标注；敏感值一律不落文档
> **本次是否改代码**：否。本文仅产出分析结论与治理建议。

## 0. 结论先行（TL;DR）

**一句话结论**：

> 三者**不是同一个代码库的三份拷贝**，而是同一「KTV 门店数字化」产品族在 12 个月内的**三次分叉**：
> **Clube-Management-System（2025-10，最早、功能最全、仍活跃）** 与 **Futuristic-Dashboard（2026-05，v0 重构版、静态演示；冻结决策见 `17`）** 同源不同实现；
> **Club-Ops（2026-05 从 Dashboard 脚手架派生，2026-10 重构为多店 SaaS）** 是 Dashboard 的直接下游。
>
> 当前真正的“混淆”不在代码里混用，而在**命名、端口、域名、文档、成熟度声明**五处重叠。

| # | 结论 | 证据强度 | 关键证据 |
|---|---|---|---|
| 1 | Club-Ops 的前端骨架来自 Futuristic-Dashboard（v0 系脚手架） | **高置信** | 初始提交 `8c612a9` 的 143 个文件中 58 个与 Dashboard 逐字节一致（40.6%），其中 45 个是 shadcn/ui 原语；当前仍有 58/88 同路径文件一致 |
| 2 | Dashboard 与 Clube-Management-System 同为 v0 系 KTV 原型后代，但**代码零复用** | **已证实** | 60 个同名源码路径，内容一致 **0**；Dashboard 包名 `my-v0-project`，CMS 首提交根目录含 `v0.config.json`（`submission_tag: ktv-v0-final`） |
| 3 | Club-Ops 与 Clube-Management-System **无代码血缘**，仅共享文档 | **已证实** | 66 个同名源码路径仅 `components/ui/spinner.tsx` 完全一致；`docs/` 下有 **10 份逐字节一致**文档（8 份团队规范 + 2 份艺人管理） |
| 4 | 命名体系已分裂：`Clube` / `Club` / 智慧商家 / 启智KTV 四套叫法并存 | **已证实** | CMS 内 `Clube` 出现 47 次（21 个文件）、`clube` 168 次；`Clube` 不是英文单词，疑为 `Club` 笔误；域名 `clube.yyc3.top` |
| 5 | 本地端口与数据库端口存在实际冲突 | **已证实** | CMS `dev -p 3030`、Club-Ops `next dev --port 3030`；CMS 移动端默认 API `localhost:3030`；Dashboard 文档写 3002、脚本默认 3000；CMS PG 5432、Club-Ops PG 5433 |
| 6 | CMS 的“生产部署”声明与其构建形态自相矛盾 | **高置信（未联网核查 Actions）** | CMS `next.config` 为 `output: 'standalone'`，但 `deploy-pages.yml` 先 `mv app/api _api_disabled` 再构建、写 `out/CNAME` 并上传 `out`；`prepare-standalone.mjs` 不生成 `out`。93 个 API 路由无法在 Pages 静态站运行 |

**建议动作（详见第 9~11 章）**：

1. 先做**产品族归属决策**（推荐：Club-Ops 为多店 SaaS 主线；CMS 作为能力矿/存量系统；Dashboard 归档）。
2. 立刻统一**命名与端口注册表**（`Clube → Club`、一项目一端口、一域名一应用）。
3. 文档只保留**一份团队规范源**，其余仓库改为链接，停止复制。
4. CMS 若继续作为“生产系统”，必须迁到可运行 Node/容器的托管环境，不能用 GitHub Pages 承载 93 个 API。

**解读**：
- CMS 是**最早的业务原型**（2025-10），并已积累真实门店语义（启智、商品、艺人、仓库）。
- Dashboard 是 2026-05 的**v0 重构/再生成版本**，定位更“品牌化”，但停留在静态演示。
- Club-Ops 是 Dashboard 的**下游派生**（不是 CMS 的下游），随后走上与两者都不同的多租户 SaaS 路线。

| 系统设置 | ⬜ 占位 | 🟡 设置 Mock | 🟡 打印/轮播/四舍五入/存储/VOD 页面齐全，无 API | — |
| 移动端 | ❌ | ❌ | ✅ Expo 58（登录/看板/订单） | CMS 独有 |
| AI/IoT/5G/边缘/大数据 | ❌ | 🟡 AI 助手 + 声明 | 🟡 页面 + 75 个相关路由（ai-ops 46 / bigdata 14 / edge 8 / iot 6 / 5g 1） | 多为演示级，是否真实接入待验证 |

**重叠结论**：

- **最大三重重叠**：包厢、POS、报表/会员/库存 —— 任何需求都容易被派到错误的仓库。
- **最危险的重复建设**：艺人管理域。CMS 已实现报表与导出（2026-10-31），Club-Ops 仍把艺人域列为 Phase 3（`09-艺人管理域对接评估.md`），并复制了同一份需求文档。
- **唯一明确互补**：Club-Ops 的多租户/RLS/CSRF 安全底座 vs CMS 的仓库/艺人/移动端业务深度。

## 5. “混淆”全清单（按严重度）

### 5.1 命名混淆

| 现象 | 证据 | 影响 |
|---|---|---|

| “Management System” 与 “Ops” 语义重叠 | 两者都覆盖 POS/包厢/报表 | 无法从名称判断谁是主线、谁是存档 |

### 5.2 端口与本地运行混淆

| 项目 | Web 端口 | API/移动端 | 数据端口 |
|---|---|---|---|
| Club-Ops | **3030** | Hono **3032** | PG **5433**（Mac 主库） |
| Clube-Management | **3030**（`next dev -p 3030`） | 移动端默认 `localhost:3030` | PG **5432** |

**风险**：

- 同时启动 CMS 与 Club-Ops 会直接端口冲突；

### 5.3 域名与部署混淆

| 域名 | 归属 | 实际能力 | 问题 |
|---|---|---|---|
| `club.yyc3.top` | Club-Ops | GitHub Pages 静态导出 + Mock；真实 API 需另起 3032 | 已明确标注“预览、非生产”，尚可 |
| `clube.yyc3.top` | CMS | README 称“生产环境”；Pages 工作流却移除 `app/api` 后静态构建 | **93 个 API 无法上线**；生产声明不成立（高置信） |
| `futuristic.yyc3.top` | Dashboard | GitHub Pages 静态导出 | README 称 Production Ready，实际 Mock + 静态 |

**CMS 部署链路的具体矛盾**：

```text
next.config.mjs         → output: 'standalone'（需要 Node 运行时）
package.json build      → next build && prepare-standalone.mjs（不生成 out/）
deploy-pages.yml        → mv app/api _api_disabled → pnpm build → echo > out/CNAME → upload out/
                          ↑ 静态 Pages 无法运行 93 个 API；且 out/ 不会由 standalone 构建生成
README                  → 生产环境 https://clube.yyc3.top
```

**结论**：CMS 要么是“功能演示站”（那就不能在 README 写生产 SLA），要么是“真实生产系统”（那就必须迁到 Node/容器托管并恢复 API）。**两种定位不能同时成立。**

## 8. 归属与主线决策（需负责人确认）

> 这不是纯技术选择，取决于「谁在服务真实门店、谁有真实数据、谁在产生收入」。以下给出三种可执行方案。

### 8.1 三种方案

| 方案 | 主线 | 其余定位 | 优点 | 代价/风险 |
|---|---|---|---|---|
| **A（推荐）** | **Club-Ops** 作为多店 SaaS 主干 | CMS = 能力矿/存量系统（按模块吸收）；Dashboard = 归档 UI 参考 | 安全底座最好（RLS/CSRF/限流/审计）；多租户模型清晰；文档与测试最规范；当前会话持续投入 | 需从 CMS 迁移艺人/仓库/移动端能力；CMS 存量用户需过渡方案 |
| B | **CMS** 作为生产经营系统 | Club-Ops 作为 POS/包厢子应用；Dashboard 归档 | 功能最全、有真实门店语义、移动端现成 | 部署形态必须重构（standalone 托管）；安全/多租户需补齐；技术债最大（93 API + 遗留配置） |
| C | 三线并行，按域切分 | Ops=收银、CMS=后台、Dashboard=展示 | 短期不改现有分工 | 维护成本最高；三套认证/DB/UI 长期分叉；混淆不会消失 |

### 8.2 推荐边界（方案 A）

| 能力 | 归属 | 说明 |
|---|---|---|
| 多租户/门店隔离/会话/权限 | **Club-Ops** | RLS + HttpOnly + CSRF 已闭环，作为平台底座 |
| 包厢/POS/账单/支付 | **Club-Ops** | 交易事实唯一写入源 |
| 艺人域 | **先冻结，评审后二选一** | 若 CMS 已生产使用，则 CMS 保留写入、Ops 只读；否则迁入 Ops Phase 3 |
| 仓库/采购/寄存/报损 | **Club-Ops Phase 3 吸收 CMS 设计** | 复用 CMS 页面信息架构，重写数据层 |
| 移动端 | **Club-Ops 后续** | 等 Web API 稳定后以 Expo 或 PWA 接入，避免维护两套 API 客户端 |
| AI/IoT/5G/边缘 | **降级为“展示/实验”** | 无真实设备与数据前，不进入生产承诺 |
| Dashboard | **已归档（ARCHIVED）** | 保留只读演示与 UI 参考；停止功能开发与生产声明。2026-11-01 已执行：提交 `33393d4`、标签 `archive-2026-11-01`、GitHub `isArchived=true`（见 `17`） |

### 8.3 决策所需事实（待确认）

1. CMS 当前是否服务真实门店？是否有付费客户/真实营业数据？
2. `clube.yyc3.top` 是否真的在对外服务？API 是否可用？
3. 艺人域由谁维护、数据在哪张库？
4. Dashboard 是否还有外部引用/演示需求？
5. 是否允许重命名仓库/包/域名（会产生 clone URL、CI、徽章、DNS 变更）？

> **在以上事实确认前，不建议做任何跨仓库代码合并或数据库合并。**

## 10. 防混淆工程化措施

### 10.1 仓库级

| 措施 | 说明 | 优先级 |
|---|---|---|
| 三仓 README 顶部加“项目族边界”块 | 一句话定位 + 与另两个项目的关系 + “不要在这里做什么” | P0 |
| 统一状态徽章 | `Preview` / `Beta` / `Production` 三档，Production 必须附证据链接 | P0 |
| 端口/CNAME/域名清单 | 写入 README 与 `docs/`，CI 校验唯一性 | P0 |
| 归档标记 | Dashboard README 加 `ARCHIVED`，关闭 issue/PR 模板或引导到主仓 | P1 |
| CODEOWNERS | 按业务域指定 owner，跨仓改动需双人评审 | P1 |

### 10.2 文档级

| 措施 | 说明 |
|---|---|
| 规范单一源 | 团队规范只保留在 Club-Ops（或独立 `YYC3-Standards` 仓），CMS/Dashboard 改为链接 |
| 艺人需求单一源 | 指定唯一文档与唯一实现仓；另一仓删除副本或标注“引用” |
| 产品族索引 | 新建 `docs/PORTFOLIO.md`：三仓定位、域名、端口、数据库、Owner、状态、决策记录 |
| 会话目录规范 | 每次审核在**主线仓**建档；其他仓只记录“变更影响” |
| 状态同步 | README 徽章数据由 CI 生成，禁止手写测试数/覆盖率 |

### 10.3 CI/CD 级

| 措施 | 说明 |
|---|---|
| 部署矩阵 | 每个域名只允许一个 workflow 部署；跨仓部署需人工审批 |
| 唯一性校验 | CI 检查：CNAME 不重复、端口不重复、包名不含 `v0`、不新增 `Clube` |
| 安全扫描 | `gitleaks` / `pnpm audit` / 明文口令规则；阻断 `*.config.json` 中的 `password` |
| 质量门禁统一 | 三仓统一下限：typecheck 0 error、lint 0 error、测试通过、构建通过 |
| 共享 reusable workflow | `YYC3-Cube/.github` 统一 CI 模板，减少三套脚本漂移 |

### 10.4 代码共享策略（分阶段）

**不要现在直接合并**，按以下顺序：

1. **先统一工具链**：Next 16 + Tailwind 4 + TypeScript strict + Vitest（CMS 从 Jest 迁移或反过来统一）。
2. **抽取 `@yyc3/club-ui`**：以 Club-Ops 的 new-york + Tailwind 4 为基线，发布内部包或私有 registry。
3. **抽取 `@yyc3/club-domain`**：`money.ts`（分单位）、`pricing.ts`（15 分钟进位）、房间状态机、角色/权限枚举。
4. **统一契约**：以 `contracts/openapi.yaml` 为唯一 API 事实源；CMS 的艺人/仓库接口先映射到同一错误码与分页语义。
5. **认证对接**：先做“网关级 SSO/Token 交换”，不强行统一实现。

### 10.5 “不要做”清单

- ❌ 不要把 CMS 与 Club-Ops 直接 merge（Next 15/16、Tailwind 3/4、Jest/Vitest、三套认证）。
- ❌ 不要共用一套数据库 schema 做双写（先定唯一写入源，再用 ETL/只读视图）。
- ❌ 不要用同一个 3030 同时跑两套应用。
- ❌ 不要把 Dashboard 的 “Production Ready” 文案复制到其他仓库。
- ❌ 不要再复制第三份团队规范。
- ❌ 不要在未确认业务归属前迁移艺人域数据。
