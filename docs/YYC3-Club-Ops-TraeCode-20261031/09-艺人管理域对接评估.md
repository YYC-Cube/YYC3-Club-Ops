# 🎭 艺人管理域对接评估

## 1. 文档来源

- `docs/YYC3-艺人管理-开发文档/YYC3-艺人管理-开发文档.md`（569 行，V2.0 合并版）
- `docs/YYC3-艺人管理-开发文档/YYC3-艺人管理系统架构图.html`

该文档描述的是 **KTV / 商务会所 / 夜总会门店的艺人（技师）管理后台**，不是当前包厢收银系统的替代品，而是同一门店运营体系中的**独立业务域**。

## 2. 规模与结构

| 维度 | 内容 |
| --- | --- |
| 菜单/页面 | 28 项 |
| 业务域 | 8 个（101 档案、102 展示、103 考勤上钟报备、104 台费资金、105 台票、106 订单预约评价、107 系统参数、108 报表） |
| 角色 | 超级管理员、店长/主管、前台/钟房、财务、艺人（移动端） |
| 核心闭环 | 主数据配置 → 报备签到 → 派单上钟 → 下钟计费 → 台费/台票扣减 → 评价 → 报表对账 |
| 多店要求 | 明确“支持多门店独立运营”，需按门店隔离配置、人员、报表 |

## 3. 与当前架构的复用点

| 当前能力 | 艺人域复用方式 |
| --- | --- |
| `Tenant` / `Store` / `Session` | 艺人、组别、考勤、台费、报表全部按 `storeId` 作用域 |
| `Room` + 房间状态机 | 上钟必须绑定包厢；上钟置为 `occupied`，下钟回到 `available` |
| `lib/pricing.ts` | 已实现“超时 15 分钟进位 + 最低 1 小时”，可直接用于艺人下钟计费 |
| 分单位金额 `lib/money.ts` | 台费、充值、扣费、台票、报表统一用“分” |
| 真实会话/门店授权 | 艺人移动端扫码登录、前台/店长权限控制 |
| OpenAPI + 服务层 | 艺人域新增契约与 Service，不另起一套模型 |

## 4. 需要新增的领域模型（Phase 3）

> 以下为建议模型，需在产品评审后冻结，不在本次 API 任务中实现。

| 模型 | 关键字段 |
| --- | --- |
| `Artist` | tenantId、storeIds、groupId、levelId、艺名、手机号、身份证、审核状态、展示状态、上下班时间、上钟规则 |
| `ArtistGroup` | storeId、名称、主管、业绩指标、备注 |
| `ArtistLevel` | storeId、等级、包厢类型单价、一口价小费、生效状态 |
| `ArtistAttendance` | storeId、artistId、报备/签到/签退时间、补打卡、审批状态 |
| `ArtistClockSession` | storeId、artistId、roomId、包厢类型、开始/结束时间、计费小时、单价、金额、状态（上钟/串台/下钟） |
| `ArtistFeeAccount` | storeId、artistId、余额、累计充值、累计扣费 |
| `ArtistFeeTransaction` | storeId、artistId、类型（充值/上钟扣费/手动扣费）、金额、关联上钟记录、操作人 |
| `ArtistTicket` | storeId、票种、价格、有效期、状态 |
| `ArtistTicketTransaction` | storeId、ticketId、购买/使用、金额、关联订单、操作人 |
| `ArtistOrder` | storeId、artistId、roomId、预约/订单、金额、状态 |
| `ArtistReview` | storeId、artistId、订单/房间、评分、内容、时间 |
| `ArtistSetting` | storeId、报备开关、签到后可签退时长、手动扫码下钟、未签到上钟、包厢计费规则、上钟模式 |

所有模型强制 `storeId`，并通过会话授权 + 服务端 RLS 做隔离。

## 5. 与房间 API 的联动

艺人上钟会改变房间状态，必须与当前房间 API 统一：

```text
派单上钟：
  POST /stores/{storeId}/rooms/{roomId}/start
  → room.status = occupied
  → 创建房间订单
  → 同时创建 ArtistClockSession（artistId、roomId、startedAt）

下钟结算：
  POST /stores/{storeId}/rooms/{roomId}/checkout
  → 计算房间/艺人均可复用的计费时长
  → room.status = cleaning
  → 关闭房间订单
  → 扣减艺人台费 / 核销台票
  → 写台账与报表维度
```

注意：当前房间 `start` 未携带 `artistId`，Phase 3 需要扩展请求体与订单模型；同时要明确“一个包厢多艺人（串台）”的计费拆分规则。

## 6. 分期建议

| 子阶段 | 范围 | 依赖 |
| --- | --- | --- |
| 3A 艺人主数据 | 艺人档案、组别、等级、包厢类型/单价、注册二维码 | 门店/权限 |
| 3B 现场运营 | 实时状态、报备、上下钟、包厢房号管理、补打卡 | 3A + 房间 API |
| 3C 资金与报表 | 台费充值/扣费/流水、台票、订单预约、评价、报表 | 3B + 支付/对账 |
| 3D C 端与移动端 | 艺人展示、扫码登录/绑定、自助报备/上下钟 | 3C + 移动端 |

不建议一次性实现 28 个页面；先做 3A + 3B 的闭环，再进入资金域。

## 7. 风险与缺口

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 范围巨大 | 28 模块 / 8 域，当前无任何实现 | 分期、按业务域验收 |
| 敏感信息 | 身份证、照片、手机号、位置 | 加密存储、最小权限、脱敏展示、审计 |
| 资金账 | 台费、台票、充值、扣费、退款 | 服务端事务 + 分单位 + 幂等 + 对账 |
| 串台/多艺人 | 一房多艺人、计时拆分 | 先定计费与分摊规则，再写模型 |
| 移动端 | 艺人扫码登录、自助操作 | 独立轻量端 + 会话/二维码安全 |
| 门店配置 | 计费、报备、上钟模式按门店隔离 | `ArtistSetting` + 门店配置版本化 |
| 报表对账 | 10 张报表，维度多 | 先定义事实表与口径，再做聚合 |
| 文档缺口 | 第 13–25 项页面细节待补充 | 业务方补齐截图/字段 |

## 9. 结论

艺人管理是当前多店 SaaS 的**下一阶段独立业务域**，与房间/计费/门店上下文高度复用，但规模远大于当前包厢闭环。建议：

1. 先把当前房间真实 API 与 PostgreSQL/RLS 稳定；
2. 再以 3A（主数据）+ 3B（上下钟）作为 Phase 3 第一冲刺；
3. 资金域必须在支付/对账/审计方案确定后启动。
